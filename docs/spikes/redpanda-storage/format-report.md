## 1. On-disk segment format — self-contained, walkable, but NOT byte-identical to Kafka

A `.log` segment is a plain concatenation of record batches: fixed 61-byte header + records payload, no file-level header/footer, no framing between batches. A standalone reader can walk it: read 61 bytes, get `size_bytes`, skip/read `size_bytes - 61` payload, repeat. `continuous_batch_parser` does exactly this (`storage/parser.h:87-140`, `parser.cc` `read_header`/`consume_records`).

**Header layout** (`model/record.h:480-561`, packed size asserted 61 at `record.h:776-790`):
`header_crc(4) | size_bytes(4,int32) | base_offset(8) | type(1) | crc(4) | attrs(2) | last_offset_delta(4) | first_timestamp(8) | max_timestamp(8) | producer_id(8) | producer_epoch(2) | base_sequence(4) | record_count(4)`.

**Differences vs Apache Kafka's on-disk batch format** (also 61 bytes) — a Kafka segment reader will NOT parse this:
- **Endianness**: header scalars are serialized via `reflection::adl`, which is **little-endian** (`reflection/adl.h:220` `ss::cpu_to_le`); Kafka is big-endian. Serialization/deserialization in `storage/record_batch_utils.cc:52-92` (`parse_header`) and `:95-116` (`batch_header_to_disk_iobuf`), written by `segment_appender::append(const model::record_batch&)` at `storage/segment_appender.cc:111-119` (header iobuf then `batch.data()` verbatim).
- **Field order/meaning**: Redpanda leads with `header_crc` (crc32c over the header fields themselves, redpanda-only; validated at `parser.cc:144-165`, recomputed on rewrite `parser.cc:322-323`) and `size_bytes` before `base_offset`; Kafka leads with `baseOffset` then `batchLength`. Kafka's `partitionLeaderEpoch(4) + magic(1)` are replaced by the 1-byte redpanda `record_batch_type` (`record.h:542-543` — "redpanda extension"). Raft term is *not* on disk (`record.h:485-527` — `ctx.term` excluded from disk format).
- `size_bytes` counts the whole batch **including** the 61-byte header (`record.h:826-829`); Kafka's `batchLength` excludes the first 12 bytes.
- **Non-data batches interleaved**: the log contains raft configuration, tx fences, archival metadata etc. as first-class batches (`record_batch_type`), so logical Kafka offsets ≠ log offsets (see caveat below).

**Records payload is Kafka-compatible**: after the header, records are the exact Kafka v2 record encoding — zigzag varints for length/timestamp_delta/offset_delta/key/value/headers (`model/record_utils.cc:217-261` `append_record_to_buffer`; `crc` at `record.h:544-546` is the Kafka-style CRC over attrs-onward). **Compression**: producer-compressed payloads are stored as-is; `attrs` carries the codec bits; validity checked at `segment.cc:553-557`; compaction decompresses internally (`segment.cc:519-525` `model::decompress_batch`). A direct reader must handle all Kafka codecs to extract one value.

## 2. Offset index — yes, sparse offset→bytepos per segment (`.base_index`)

- `segment_index` maintains three parallel columns: `relative_offset (u32) | relative_time (u32) | filepos (u64)` (`storage/index_state.h:83-85`, entry struct `:150-163`), i.e. 16 bytes/entry.
- **Sparsity**: one entry per `default_data_buffer_step = 4096*8 = 32 KiB` of batch bytes (`storage/segment_index.h:152`, used at `segment.cc:818-822`), byte-accumulated in `segment_index::maybe_track` (`segment_index.cc:133-157`, `_acc += hdr.size_bytes` then `index_state::maybe_index(acc, step, ...)` at `index_state.h:273-283`). Tracking is hooked in the hot append path at `segment.cc:585` and during recovery `log_replayer.cc:67`.
- **Query**: `index_state::find_nearest(model::offset)` returns `{offset, timestamp, filepos}` (`index_state.h:174`); the reader then scans forward batch-by-batch from `filepos`. `find_nearest(timestamp)`, `find_above/below_size_bytes` also exist (`:176-180`).
- **Persistence**: flushed as a **serde envelope** (`index_state` version 11, `index_state.h:134-135`) — `segment_index::flush_to_file` writes `serde::to_iobuf(_state)` (`segment_index.cc:255-267`). The legacy pre-serde layout is documented in the comment at `index_state.h:117-133` (version, size, xxhash checksum, columns). So: persisted, checksummed, but a redpanda-internal serde format (versioned, has evolved 11 times) — parseable but a moving target for an external reader.

## 3. Compaction — lives in `src/v/storage/` + `src/v/compaction/`; and yes, key→offset structures already exist

**Driver**: `log_manager::housekeeping_loop` fires on `log_compaction_interval_ms` (`storage/log_manager.cc:146-196`) → `disk_log_impl::housekeeping` (`disk_log_impl.cc:1378-1399`) → `do_gc` then `do_compact` (`:1424-1460`), choosing `adjacent_merge_compact` (`:551`) or the default `sliding_window_compact` (`:688`), with chunked variant `:1480`.

**Segment rewrite + swap** (`storage/segment_utils.cc`): `do_self_compact_segment` (`:573-644`) writes deduplicated data to `<segment>.log.staging` (`fs_utils.cc:120-122`), evicts readers (`segment_utils.cc:622` `readers_cache.evict_segment_readers`), then `do_swap_data_file_handles` (`:533-547`) does `ss::rename_file` over the original — **byte positions of surviving batches change; the original file identity survives but contents are rewritten**. Adjacent-merge concatenates into `.log.compaction.staging` (`fs_utils.cc:115-117`) via `concatenate_and_rebuild_target_segment` (`segment_utils.cc:1217-1323`), swaps into the front segment, and removes the rest from the `segment_set` (`disk_log_impl.cc:1098-1200`). Each rewrite bumps the segment's `generation_id` (`segment.h:275-276`), used to detect concurrent modification (`generation_id_mismatch_exception`, `disk_log_impl.cc:1170`).

**Key→offset structures — three already exist:**
1. **`.compaction_index` file, per segment, persisted, built at append time**: for compacted topics, every appended batch's record keys are written through `compacted_index_writer` → `spill_key_index` (`storage/spill_key_index.h:32`, factory `spill_key_index.cc:411-418`; wired at segment roll `segment.cc:893-906`; fed from the append path `segment.cc:604` → `compaction_index_batch`, decompressing if needed `:499-525`). Entry = `{entry_type, compaction_key, offset, delta}` (`storage/compacted_index.h:126-141`); `compaction_key` = batch_type + control-bit prefix + raw key bytes (`compaction/key.h:20-23`, `storage/compaction_key.{h,cc}`). File ends with a CRC'd, versioned footer (`compacted_index.h:47-85`). **Note: it maps key→offset, not key→byte position, and it is an append-order log of keys (with dups), not a lookup structure.** Rebuildable when missing/corrupt (`segment_utils.h:47-70`).
2. **In-memory `key_offset_map`** (`compaction/key_offset_map.h:26-52`; `simple_key_offset_map` `:87-104`, `hash_key_offset_map` `:119+` storing sha256 digests, not keys): built by `build_offset_map` from the per-segment compacted indexes (`storage/segment_deduplication_utils.h:24-51`) during `sliding_window_compact` (`disk_log_impl.cc:770-796`), then `deduplicate_segment` rewrites each segment keeping only latest-offset keys (`segment_deduplication_utils.h:55-60`). **Ephemeral — discarded after the pass.**
3. `index_state` compaction bookkeeping (clean/self compact timestamps, tombstone flags) persisted per segment (`index_state.h:222-255`).

## 4. Hookability — natural seams

- **(b) Append-time indexing**: the cleanest precedent is exactly what you want minus byte positions: `compacted_index_writer` (abstract, `storage/compacted_index_writer.h`) invoked per batch from `segment::append` (`segment.cc:604`, `compaction_index_batch` `segment.h:326-327`). A sibling writer receiving `(key, offset)` per record is a drop-in pattern. For byte positions, `segment::append` already has `start_physical_offset` in hand where it calls `_idx.maybe_track(hdr, now, start_physical_offset)` (`segment.cc:585`) — that call site gives you `(batch header, physical file pos)` per append; `segment_index::maybe_track` (`segment_index.cc:133`) is the single choke point. Durability signal: `segment_appender::set_stable_offset_callback` (`segment_appender.h:165`, wired at `segment.cc:63`) fires as bytes become stable on disk.
- **Reading/scanning**: `batch_consumer` (`storage/parser.h:34-84`) is the canonical visitor — `consume_batch_start(header, physical_base_offset, size_on_disk)` hands you exactly the byte position per batch; a background fiber could rebuild key→(offset, bytepos) by driving `continuous_batch_parser` over a segment.
- **(a) Compaction/rewrite events**: there is **no generic "segment rewritten" event bus**. Existing seams: (i) `stm_hookset` (`storage/types.h:130+`) — compaction already calls into registered state machines (passed through `do_compact_adjacent_segments` `disk_log_impl.cc:1160-1169`, `build_offset_map` `segment_deduplication_utils.h:47`, `compaction_reducers.h:146,279`), the natural place to add a "batch survived compaction at new position" callback; (ii) `readers_cache::evict_segment_readers` (`segment_utils.cc:622,1278`) is invoked on every rewrite — an external index needs the equivalent invalidation; (iii) `segment::generation_id` (`segment.h:275`) is a per-segment version counter you can snapshot to detect staleness; (iv) `log::monitor_eviction` (`storage/log.h:159`, impl `disk_log_impl.cc:476-516`) signals prefix truncation; (v) `log::notify_compaction_update` (`log.h:231`, `disk_log_impl.cc:3779`) is only a config toggle, not an event. Practical takeaway: **any external byte-position index is invalidated wholesale per segment on every compaction rewrite** — plan to treat `(segment base_offset, generation_id)` as the cache key and rebuild from the swapped file, or index key→offset only and resolve offset→bytepos via `.base_index` at read time (positions in `.base_index` are rewritten atomically with the swap: `do_copy_segment_data` returns a fresh `index_state`, `segment_utils.cc:344,609`).
- Note also Redpanda's own embedded KV store, `storage/kvstore.{h,cc}` — an existence proof of a key-value abstraction over this log machinery.

## 5. Tiered storage caveat — confirmed, local reads can miss

With Shadow Indexing/Tiered Storage, retention is overridden by **local** targets (`retention.local.target.bytes/ms`): `disk_log_impl::apply_local_storage_overrides` / `maybe_apply_local_storage_overrides` (`disk_log_impl.cc:1224-1304,1373-1375`); GC computes an eviction point and signals it via the `monitor_eviction` promise (`disk_log_impl.cc:476-516`); the upper layer prefix-truncates local segments **after upload**, deleting the `.log` files locally. Reads below the local start offset go through `cloud_storage::remote_partition` / `remote_segment` with its own chunk cache and its own remote index format (`src/v/cloud_storage/remote_partition.h`, `remote_segment.h:51`, `remote_segment_index.{h,cc}`, `segment_chunk_api.cc`). A byte-position read against the local filesystem will simply find the file gone (or, without strict local retention, only recent data present). Any direct-read product must either pin local retention or replicate the remote-fetch path.

## Cross-cutting caveat not in your list: offset translation

The `(partition, offset)` your KV API exposes is presumably the **Kafka** offset; on disk, batches are stored at **raft/log** offsets that include config/control batches. Translation lives in `storage/offset_translator.{h,cc}` (`offset_translator.h:43`, delta handling `:95-101`) with persisted state in `offset_translator_state.cc`. `.base_index` and `.compaction_index` are keyed by **log** offsets, so an external reader needs the translator state too (or must index by log offset from the start).

## Bottom line

A standalone seek-read of one record is mechanically feasible: `.base_index` (`find_nearest`) gives a ≤32 KiB scan window in a self-describing, checksummed batch stream, and a per-key index can piggyback on the same seams compaction already uses (`compacted_index_writer`, `maybe_track`, `batch_consumer`). The hard parts are: (1) the format is redpanda-flavored (little-endian, reordered 61-byte header, serde-versioned index files) — you are committing to tracking an internal format with no stability guarantee; (2) compaction rewrites files in place via rename, invalidating all byte positions per pass with no public event hook — you'd patch in one (`stm_hookset` or a new callback at the swap sites in `segment_utils.cc`); (3) tiered storage deletes local bytes; (4) Kafka-vs-log offset translation; (5) compressed batches force codec support and make "read exactly one value" a decompress-the-batch operation anyway.
